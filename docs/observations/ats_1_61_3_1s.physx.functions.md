The catalog has 7 entries. `ResolveKnownMethods` matches all 7
against any candidate vtable buffer; for ATS 1.61.3.1s the candidate
vtable is at RVA 0x25020A0 (118 slots).

## Provenance

Each row has a documented LEA-ref matching chain in
`rea/scripts/physx-vta-scan/README.md` § Hallazgos confirmados. The
catalog was produced by:

1. Reading the open-source PhysX 3.4 PxScene.h header to enumerate
   virtual methods.
2. Locating each method's LEA instruction in `.text` by following the
   references to the matching `PxScene::<method>` assertion string
   stored in `.rdata` (release, addActor, simulate, shiftOrigin,
   sweep).
3. **Disassembling the vtable @ RVA 0x25020A0** and matching each
   slot's function prologue to the expected public-API signature
   (raycast, overlap — these methods have no assertion strings in
   the binary).

## PxScene vtable @ RVA 0x25020A0 (118 slots)

`ResolveKnownMethods` was probed against the vtable candidate at RVA
0x25020A0 (image base 0x140000000, 118 contiguous code-pointer
slots). Of the 7 catalog VAs, **5 are exact slot matches** and 1 is
within 8 bytes of a slot (the walk-back heuristic lands on a
non-prologue instruction, so the actual function entry is a few bytes
earlier). sweep is NOT in this vtable.

| Catalog VA | Slot VA | Δ bytes | Note |
| --- | --- | --- | --- |
| `release`      `0x141AE07B6` | slot   2: `0x141AE07B0` | -6  | slot 2 has the real function entry; the int3 padding + `mov [rsp+8], rbx; push rdi; sub rsp, 0x30` prologue |
| `addActor`     `0x141AE0B62` | slot  11: `0x141AE0B60` | -2  | the body of the function; actual entry is 2 bytes earlier |
| `simulate`     `0x141AE4D80` | slot  57: `0x141AE4D80` |  0  | exact match; function prologue `sub rsp, 0x48` immediately followed by the LEA |
| `shiftOrigin`  `0x141AE6C28` | slot 117: `0x141AE6C20` | -8  | the function body; actual entry 8 bytes earlier |
| `sweep`        `0x141B06F10` | (not in 0x25020A0)     |  -  | sweep lives in a separate 5-slot run starting at RVA 0x2507C08 (slot 4) |
| `raycast`      `0x141AE1610` | slot  15: `0x141AE1610` |  0  | exact match; function prologue `mov rax, rsp; ... sub rsp, 0x490`; local struct sets `nbMaxTouches = 0x40 = 64` |
| `overlap`      `0x141AE0F70` | slot  13: `0x141AE0F70` |  0  | exact match; thin dispatcher `xor r9d, r9d; jmp 0x141AE0FD0`; the tail target's prologue has `sub rsp, 0x2c0` and sets `nbMaxTouches = 0x8 = 8` |

The 118-slot vtable at 0x25020A0 is the combined PxScene +
PxSceneExtension vtable (the PxScene API in this build has many more
virtuals than the 50ish published in PhysX 3.4 headers, and the
offset between `release` (slot 2) and `simulate` (slot 57) is ~55
slots — consistent with PxSceneExtension contributing the first ~30
virtuals before PxScene's own). Slots 16-22 have **0 external call
sites** — they are PxScene-internal methods only, never called from
the rest of the game binary.

### Earlier vtable location (RVA 0x2500EA0) was a misidentification

An earlier M3 pass documented the PxScene vtable as RVA 0x2500EA0.
That RVA was wrong — re-reading bytes there returns ASCII text from
`PxScene::addActor() ... is not valid` assertion strings, not a
vtable. The correct vtable is RVA **0x25020A0** (118 slots). The
slot 2/11/57/117 catalog matches from the earlier pass were against
the same underlying vtable data; the bytes happened to be reachable
through the wrong RVA because of a one-off address transcription
error in the previous analysis script.

## What it unlocks

- **In-process slot resolution**: when the DLL is loaded by ATS,
  `PhysXAdapter` can scan `.rdata`, find the candidate vtable at RVA
  0x25020A0, and resolve `release` / `addActor` / `simulate` /
  `shiftOrigin` / `raycast` / `overlap` slots without needing a live
  PxScene instance or full Ghidra analysis. `sweep` lives in a
  separate vtable (`PhysXAdapter` would have to scan both vtables
  to pin the sweep slot).
- **Cross-validation against TMRealWalk**: TMRealWalk uses the same
  string-based detection. If our `ResolveKnownMethods` finds >=5
  matches and the slot offsets fall in the published PhysX 3.4 SDK
  order (release at 2, addActor at 11, simulate at 57, shiftOrigin
  at 117, raycast at 15, overlap at 13), we have identified the
  vtable with very high confidence.

## How raycast / overlap were located (no assertion strings)

`PxScene::raycast` and `PxScene::overlap` do not emit assertion
strings in the binary (the SDK has no precondition check that
triggers an assert for these paths). Without a string anchor, the
LEA-walk-back chain has no first hop. The identification used:

1. **Disassembled every slot's function** in the 0x25020A0 vtable
   (118 functions, ~32 bytes each).
2. **Recognized the public-API hit-buffer init pattern** by
   inspecting each function's prologue + first 0x100 bytes for the
   `nbMaxTouches` constant:
   - `PxRaycastBuffer::PxRaycastBuffer()` initializes
     `nbMaxTouches = PX_MAX_RAYCAST_HITS` (default 0x40 = 64)
   - `PxOverlapBuffer::PxOverlapBuffer()` initializes
     `nbMaxTouches = PX_MAX_OVERLAP_HITS` (default 0x8 = 8)
3. **Slot 15's first instructions** were
   `mov rax, rsp; mov [rax+0x20], r9b; mov [rax+0x10], rdx;
    push rbp; lea rbp, [rax-0x398]; sub rsp, 0x490` — a 0x490-byte
   stack frame, consistent with raycast's larger hit buffer.
   The local-struct init at `[rbp+0x144] = 0x40` confirms raycast.
4. **Slot 13's first instructions** were
   `xor r9d, r9d; jmp 0x141AE0FD0` — a thin dispatcher that
   initializes `r9 = 0` (the PxOverlapCallback pointer default) and
   tail-calls into the real implementation at 0x141AE0FD0, which
   has a 0x2c0-byte stack frame and the local-struct init
   `[rbp+0xc4] = 0x8 = 8` — overlap.

The implementation at 0x141AE0FD0 calls the broadphase query at
`call 0x141b46b50` (matching the pattern at slot 15's call to
`call 0x141ae8490` — both delegate to the BP subsystem).

Slot 14 (0x141AE1C60) has the **5th most-called vtable method in
the entire binary** (241 call sites — same magnitude as slot 15's
36 + slot 13's 52 = ~88, suggesting slot 14 is called even more than
both raycast+overlap combined). The function is a thin dispatcher
that calls `[arg2.vtable+0x30]` and tail-jumps into 0x141AE1CF0,
which dispatches on geometry type. This is **NOT** raycast or
overlap — it appears to be some other PxScene method that takes a
shape or actor reference. The slot-VA pattern (5th most-called
overall) matches what we'd expect from `PxScene::addActor` (already
cataloged at slot 11) or `PxScene::removeActors` or similar.

The slot-by-slot frequency profile (slots 13-22):

| Slot | VA | Calls | Likely role |
| --- | --- | --- | --- |
| 13 | `0x141AE0F70` | 52 | **PxScene::overlap** (overlap thin dispatcher) |
| 14 | `0x141AE1C60` | 241 | Unknown actor-related method (5th most-called overall) |
| 15 | `0x141AE1610` | 36 | **PxScene::raycast** (full impl) |
| 16 | `0x141AE2CC0` | 0 | Internal (saves/restores MXCSR; not called externally) |
| 17 | `0x141AE2DE0` | 0 | Internal (thin type-check dispatcher, never called externally) |

| 19 | `0x141AE31D0` | 0 | Internal (decrements scene counter; not called externally) |

The high call count for slot 14 despite being NOT raycast/overlap
suggests it is the most-called PxScene method in this build (likely
`PxScene::somethingThatNeedsActorComponent` — to be confirmed by
Ghidra decompile or live breakpoint).

## Updating for a new ATS build

When a future ATS patch changes any of these methods:

1. Re-run `python scripts/physx-vta-scan/find_string_refs.py "<path>\amtrucks.exe"`
2. Update the VAs in `src/provider/PhysXAdapter.cpp` (the
   `kPhysXKnownMethods` array).
3. Add a VersionEntry row for the new build SHA in
   `src/domain/VersionTable.cpp` carrying the new VA list.
4. Re-verify slot assignments by running
   `verify_pxscene_vtable.py` (looks for the vtable candidate
   that matches the catalog VAs at slots in the published PhysX 3.4
   SDK order).

If the SDK devirtualises one of the methods entirely, replace its
catalog row with an empty name (or drop it). The matcher is
defensive — missing catalog rows are simply not matched.

If a new method's assertion string becomes available in the
binary (e.g., a future PhysX update emits a precondition check for
a new method), add it to `kPhysXProbeStrings` in
`include/walkercore/PhysXAdapter.h` so `MemoryScanFromBuffer`
counts it as a string-probe hit on next scan.
