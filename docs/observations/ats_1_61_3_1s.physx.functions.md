# ATS 1.61.3.1s — known PxScene method function addresses

Reference catalog used by `walkercore::PhysXAdapter::ResolveKnownMethods`
to map vtable entries to method names. Image base = `0x140000000` (PE
load address). VA = image base + RVA.

| Method | VA | RVA | Slot | Source |
| --- | --- | --- | --- | --- |
| `PxScene::release`     | `0x141AE07B6` | `0x1AE07B6` | TBD | LEA -> "PxScene::release(): Scene is still being simulated" |
| `PxScene::addActor`    | `0x141AE0B62` | `0x1AE0162` | TBD | LEA -> "PxScene::addActor() not allowed" |
| `PxScene::simulate`    | `0x141AE4D80` | `0x1AE4380` | TBD | LEA -> "PxScene::simulate() ..." |
| `PxScene::shiftOrigin` | `0x141AE6C28` | `0x1AE6228` | TBD | LEA -> "PxScene::shiftOrigin() not allowed" |
| `PxScene::sweep`       | `0x141B06F10` | `0x1B06F10` | TBD | LEA -> "PxScene::sweep(): first geometry object ..." |

The "Slot" column is populated by `ResolveKnownMethods` at runtime —
when a vtable candidate's pointer at `vtable_base + N*8` equals one of
the VAs, N is the slot for that method.

## Provenance

Each row has a documented LEA-ref matching chain in
`rea/scripts/physx-vta-scan/README.md` § Hallazgos confirmados. The
catalog was produced by:

1. Reading the open-source PhysX 3.4 PxScene.h header to enumerate
   virtual methods.
2. Locating each method's LEA instruction in `.text` by following the
   references to the matching `PxScene::<method>` assertion string
   stored in `.rdata`.
3. Recording `image_base + RVA` as the method's absolute VA.

## PxScene vtable @ RVA 0x2500EA0 (118 slots)

`ResolveKnownMethods` was probed against the vtable candidate that
the signature scan accepts at RVA 0x2500EA0 (image base
0x140000000, 118 contiguous code-pointer slots). Of the 5 catalog
VAs, **3 are exact slot matches** and the other 2 are within 8 bytes
of a slot (the walk-back heuristic lands on a non-prologue
instruction, so the actual function entry is a few bytes earlier):

| Catalog VA | Slot VA | Δ bytes | Note |
| --- | --- | --- | --- |
| `release`     `0x141AE07B6` | slot  2: `0x141AE07B0` | -6  | slot 2 has the real function entry; the int3 padding + `mov [rsp+8], rbx; push rdi; sub rsp, 0x30` prologue |
| `addActor`    `0x141AE0B62` | slot 11: `0x141AE0B60` | -2  | the body of the function; actual entry is 2 bytes earlier |
| `simulate`    `0x141AE4D80` | slot 57: `0x141AE4D80` |  0  | exact match; function prologue `sub rsp, 0x48` immediately followed by the LEA |
| `shiftOrigin` `0x141AE6C28` | slot 117: `0x141AE6C20` | -8 | the function body; actual entry 8 bytes earlier |
| `sweep`       `0x141B06F10` | (not in 0x2500EA0)    |  -  | sweep lives in a different vtable (5-slot run starting at RVA 0x2507C08, slot 4) |

The 118-slot vtable at 0x2500EA0 is the combined PxScene +
PxSceneExtension vtable (the PxScene API in this build has many
more virtuals than the 50ish published in PhysX 3.4 headers, and
the offset between `release` (slot 2) and `simulate` (slot 57) is
~55 slots — consistent with PxSceneExtension contributing the first
~30 virtuals before PxScene's own). Slot 95-97 contain VAs in the
0x141B06xxx range close to `sweep` (0x141B06F10), but no exact match
— `ResolveKnownMethods` returns `sweep_slot = -1` against this
vtable.

## PxScene::raycast and PxScene::overlap — not cataloged

The PhysX 3.4 / 4.1 SDK emits assertion strings for `PxScene::sweep`
but not for `raycast` or `overlap` (those paths have no
precondition check that triggers an assert). Without a string
anchor, the LEA-walk-back chain has no first hop. To find their
VAs we need one of:

- A live PxScene instance and a debugger breakpoint on
  `PxScene::raycast(...)` / `PxScene::overlap(...)`. ATS calls
  these internally for AI traffic; setting a hardware breakpoint
  on the first call after F5 (Enter) and reading the resolved
  return address gives the function VA directly.
- A Ghidra decompile of `PxScene::raycast` and `PxScene::overlap`
  to pin them to slot positions in the 0x2500EA0 vtable.
- A behavior test: stand at a known collision distance from a
  wall, hook `PhysXAdapter::SphereSweep` to log the
  `__cdecl`-resolved return addresses, and read the slot
  pointers off the `this` vtable.

### Byte-level analysis of vtable @ 0x2500EA0 slot candidates

To narrow down the candidates without a Ghidra decompile, we
walk backward from each slot VA and look for `0xCC` (int3)
padding that signals an MSVC function boundary. A real function
entry sits immediately after a CC run; a slot VA in the middle
of a function (e.g., after the prologue already ran) is
*not* a function entry, even though the vtable still points to
it as a code pointer.

| Slot | VA | CC bytes before | Real entry? | Notes |
| --- | --- | --- | --- | --- |
| 13 | `0x141AE0F70` | 9 | NO | body bytes are `45 33 c9 e9 58 00 00 00` = `xor r9d, r9d; jmp +0x58` — this is a tail of a function, not an entry |
| 14 | `0x141AE1C60` | 4 | YES | function prologue `mov [rsp+8], rbx; mov [rsp+0x10], rsi; push rdi; sub rsp, 0x30` — small leaf function (sphere overlap or batch query?) |
| 15 | `0x141AE1610` | 14 | YES | function prologue `mov rax, rsp; mov [rax+0x20], r9b; mov [rax+0x10], rdx; push rbp; lea rbp, [rax-0x398]; sub rsp, 0x490` — large stack frame (likely raycast with hit buffer) |
| 27 | `0x141AE2FA0` | 7 | NO | tail of a function |
| 28 | `0x141AE2FB0` | 10 | NO | tail of a function |
| 29 | `0x141AE6020` | 0 | (entry) | real entry; bytes immediately follow non-CC data |
| 95 | `0x141B06200` | 6 | YES | in 0x141B0xxxx range, similar to sweep |
| 96 | `0x141B06370` | 5 | YES | in 0x141B0xxxx range |
| 97 | `0x141B062D0` | 8 | YES | in 0x141B0xxxx range |

**Best unconfirmed candidates** for raycast/overlap based on the
public API order (PxScene has 9 methods between `addActor` and
`getGravity`, then `getGravity`/`setGravity`, then the dominance
matrix, then `raycast`/`sweep`/`overlap` at the next 3 slots):

- `0x141AE1610` (slot 15) — large stack frame (0x490 bytes) is
  consistent with raycast's hit buffer allocation. If this is
  `PxScene::raycast`, then `PxScene::sweep` is at slot 16 or 17
  and `PxScene::overlap` is the next slot. Slot 16 is
  `0x141AE2CC0`, slot 17 is `0x141AE2DE0`.
- `0x141AE1C60` (slot 14) — small stack frame, leaf function. If
  this is `PxScene::sweep` (sweep is a thin wrapper in some
  builds), then `raycast` is at slot 13 (the tail) and `overlap`
  is at slot 15.

These assignments are **not** confirmed. None of the candidate
VAs are added to `kPhysXKnownMethods`; the catalog stays at 5
rows until live verification pins the right slots.

## What it unlocks

- **In-process slot resolution**: when the DLL is loaded by ATS,
  `PhysXAdapter` can scan `.rdata`, find a candidate vtable, and
  resolve `release` / `addActor` / `simulate` / `shiftOrigin` /
  `sweep` slots without needing a live PxScene instance or full
  Ghidra analysis.
- **Cross-validation against TMRealWalk**: TMRealWalk uses the same
  string-based detection. If our ResolveKnownMethods finds >=2
  matches and the slot offsets fall in the published PhysX 3.4 SDK
  order, we have identified the vtable with very high confidence.

## Updating for a new ATS build

When a future ATS patch changes any of these methods:

1. Re-run `python scripts/physx-vta-scan/find_string_refs.py "<path>\amtrucks.exe"`
2. Update the VA in `src/provider/PhysXAdapter.cpp` (the
   `kPhysXKnownMethods` array).
3. Add a VersionEntry row for the new build SHA in
   `src/domain/VersionTable.cpp` carrying the new VA list.

If the SDK devirtualises one of the methods entirely, replace its
catalog row with an empty name (or drop it). The matcher is
defensive — missing catalog rows are simply not matched.

If a new method's assertion string becomes available in the
binary (e.g., a future PhysX update emits a precondition check
for `raycast` or `overlap`), add it to `kPhysXProbeStrings` in
`include/walkercore/PhysXAdapter.h` so `MemoryScanFromBuffer`
counts it as a string-probe hit on next scan.
