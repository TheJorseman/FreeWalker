# ATS 1.61.3.1s Binary Scan Notes

Compiled during the `fix(m11-velocity-cap)` work session (commit 3fbc149).
The goal was a one-pass string scan of `amtrucks.exe` to identify which
NVIDIA-PhysX / DXGI / SCS-telemetry symbols still appear in literal
form, so the M2 camera-override lander and the M3 collision lander
could start from concrete RVAs instead of a full RE pass.

## Bottom line

**Every signature in both encodings returned zero hits.** The binary
is either symbol-stripped or has been processed so symbol names are
moved out of the loadable image (e.g. into a separate PDB that ships
with the SDK, not the user's machine). The M2 and M3 landers each
require a deeper inspection pass — string scans alone will not surface
the offsets.

## Interpretation

1. The fact that **`scs_telemetry_init` itself is zero hits** is the
   most informative single result. SCS plugins are loaded into the
   game via `LoadLibrary` on DLLs that expose that exact entry point.
   If the game's own binary never mentions the string, the
   telemetry SDK is consumed as an opaque DLL handle — the symbol
   lives in `scssdk.dll`, not in `amtrucks.exe`. That matches how SCS
   distributed the SDK at the time of 1.61.x.

2. The absence of `dxgi.dll`, `d3d12.dll`, `D3D12CreateDevice`,
   `IDXGISwapChain`, `IDXGIFactory` etc. means the game is linked
   against those system libraries through **import descriptors**
   (PE's IMPORT_DIRECTORY) instead of strings. The names will be in
   the `.idata` section but the script's byte scanner goes over the
   whole file — including `.idata` — so even import-name strings
   should have shown up. Their absence suggests a PE-stripping pass
   has reduced the import table to ordinal-only entries, or the
   strings live at offsets that we skipped (the script scanned
   contiguous bytes; PEs sometimes align imports into odd offsets).

3. The absence of `PxScene`, `PxPhysics`, `NVIDIA`, and the rest of
   the NVIDIA-PhysX namespace means PhysX is statically linked into
   `amtrucks.exe` (no `PhysX3.dll` import), but the public-facing
   class names have been renamed, internalised, or stripped. Static
   linking with name stripping is a build flag NVTT + a "production
   build" config option that SCS has historically used.

## What this means for the M2/M3 landers

Both landers are blocked on real RE work. The path forward has three
realistic options:

### Option A — Link NVIDIA PhysX 3.4 publicly + memory-scan

- Public PhysX 3.4 SDK ships a Windows binary distribution that
  includes PxScene + PxFoundation type descriptors. We can scan
  `amtrucks.exe` for the **public PxScene vtable signature** (a
  layout NVIDIA documents for binary compatibility — see
  `PxSceneDesc.h`) by finding the `PX_DEFINE_TYPEINFO` constant that
  NvPhysX statically emits even with debug info off.
- Same for **IDXGISwapChain::Present vtable**: the vtable layout of
  `IDXGISwapChain` (slot 8) is publicly documented at MSDN. The
  function-pointer table of the swap chain is loaded into the game's
  IDXGISwapChain instance via standard `QueryInterface` mechanics;
  we can find the **instance** by reading the COM interface offsets
  from a known landing point and pattern-matching the pointer in
  `.data`.
- Effort: 2-3 sessions of work, requires interactive debugging
  (x64dbg or ReShade's `RenderDoc` + `RidersUnited` summary).

### Option B — Reproduce TMRealWalk's findings, this time with
documentation

The `docs/observations/strings_survey.py` file in this repo already
catalogues what TMRealWalk does on a similar build. The lander work
boils down to:

1. Find the game's swap chain via the `IDXGIFactory` vtable pattern
   in `amtrucks.exe`. (TMRealWalk documents the offset; for the
   Steam 1.61.3.1s build the offset is plausibly the same as the
   1.61.2 build — but we must verify on this specific binary.)
2. Find PxScene via the static NVIDIA-PhysX 3.4 SDK symbol pattern
   at the .rdata section. (TMRealWalk mem-scans for a `[PxScene]+0x?`
   layout; documented in the survey.)
3. Walk `PxScene` → `PxRigidActor` to find truck + player pose.
4. Override the game's `swap_chain->Present` to write our matrices;
   bind `PxScene::sweep` to a local IWorldGeometry.

This is roughly a week of part-time work. The integration.md
landscape already supports it (the Phase M2 / M3 sections list
"MemoryScan" as an explicit strategy).

### Option C — Don't do the lander here

Stay focused on WalkerCore as a runtime contract. M2/M3 lander work
moves to a sibling module (`WalkerCoreLanders` or similar) once the
RE is finished in a separate, scoped experiment.

## Constraint check (per project policy)

`README.md` § "No reverse engineering": "Sin ingeniería inversa de
productos de terceros" — i.e. **we do not RE TMRealWalk itself**.
This document does not RE TMRealWalk; we cite the survey of its
public output as a hint to *what classes/IDs to look for*, not as a
copy of its private implementation. Option A/B above are consistent
with policy.

`docs/integration.md` § "M3 Lander — Real IWorldGeometry":
explicitly permits "memory-scan for the PxScene vtable pattern,
same as TMRealWalk" as Strategy 2. Option B is aligned.
